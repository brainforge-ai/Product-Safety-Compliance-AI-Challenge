# Hurdles & Unplanned Solutioning

Running log of unexpected problems found during implementation and how we handled them. Kept concise — one entry per issue, newest at bottom of each phase.

---

## Phase 2: File Extraction

**OCR misreads digits in chemical formulas.** Tesseract reliably reads capital `O` as `0` (`H2O2` → `H202`) and occasionally a leading `C` as `€` (`C12H24O12` → `€12H24012`). Since the forbidden list contains formula entries, this risked a false **Accept** on scanned products. Captured real corrupted samples in a fixture; deferred the actual fix to later phases (see Phase 4/5 below).

**`fitz.FileNotFoundError` wasn't caught.** `PdfExtractor` only caught `fitz.FileDataError` (corrupt PDFs), missing the separate exception for a missing file path. Fixed by catching `RuntimeError` (the common base of both).

---

## Phase 3: Structured Parsing

**Numbered-list stripping almost corrupted a real ingredient.** Forbidden ingredient `1,4-Dioxane` starts with a digit; a naive bullet-stripping regex would mistake `1,` for a `"1."` list marker and truncate it to `,4-Dioxane`. Confirmed this exact ingredient appears in sample P-2025-0008. Fixed by requiring numbered markers to be followed by whitespace, not just any character.

**`expected_ingredients.json` fixture is not independent ground truth.** It was generated by running the parser itself, then eyeballed — a valid regression guard, but a systematic parser bug could satisfy both sides. Real correctness evidence lives in the hand-written synthetic unit tests instead.

---

## Phase 4: Normalization & Formula Parsing

**OCR formula correction is ambiguous without a target to check against.** Tried a combinatorial "guess which `0` should be `O`" approach in the parser itself. Traced a real failure case (`C20H4002`): multiple corrections (`H:4002`, `H:40,O:2`, `H:4,O:2`) are all syntactically valid, and neither fewest-edits nor smallest-count heuristics broke the tie correctly. **Decision:** kept `parse_formula` strict/context-free; deferred correction to Phase 5's matcher, where a specific forbidden formula acts as the oracle that disambiguates.

---

## Phase 5: Matching Pipeline

**Fuzzy matching can't satisfy both a real sample and the README's own example.** Every standard string-similarity metric tested (rapidfuzz ratio/partial/token_sort/token_set/WRatio, Levenshtein, Jaro-Winkler) scores the README's `Glucose` vs `D-Glucopyranose` (~0.65–0.76) *lower* than real sample P-2025-0024's `Sodium Laureth Sulfate` vs forbidden `Sodium Lauryl Sulfate` (~0.85–0.91) — a pair that must NOT match. No threshold can catch the true positive without false-rejecting the real sample. **Decision:** set threshold conservatively (≥90) to protect the real sample; the README's example is pushed to an open Phase 8 question (embeddings likely can't do it either — probably needs the LLM tier, which conflicts with the "zero API keys" goal).

**Formula matcher must gate correction on "parsed but wrong," not "failed to parse."** `parse_formula("H202")` *succeeds* (returns `{H: 202}`) — it doesn't return `None`. Gating the OCR-correction attempt on a `None` result would silently skip exactly the corruption it's meant to catch.

**"BHA" doesn't decompose from "Butylated Hydroxyanisole" as one word.** Generic per-word-initials only yields "BH" from the 2-word spelling. Used the legitimate alternate 3-word spelling ("Butylated Hydroxy Anisole") for the test instead of building compound-word decomposition — documented as a known limitation, not fixed.

## Phase 6: Persistence Layer

**`SQLModel.metadata.create_all()` silently created zero tables in a real run.** SQLModel only registers a table class once it's been imported somewhere in the process; `create_db_and_tables()` called `create_all()` without ever importing `infra/db/models.py`, so a real server boot produced an empty `.db` file. Every automated test passed anyway, since each test module imported the table classes directly, masking the bug. Caught only via a manual server run + `sqlite3` inspection. Fixed by importing the models module inside `create_db_and_tables()` itself. Added a subprocess-spawned regression test, since an in-process test can't fail here once any other test module has imported the models.

**Offset pagination needs a tiebreaker.** `list_evaluations` originally sorted by `created_at DESC` alone; two records with the same timestamp (plausible once Phase 7 batch-evaluates concurrently) would make offset pagination skip or duplicate rows. Fixed by tie-breaking on `id DESC`.

## Phase 7: API Layer

**Per-route exception handling shadowed the app-level 415/422 split.** `/evaluate` and `/evaluate/by-path` originally caught `AppError` locally and re-raised a generic `HTTPException(422)` — which ran *before* the global `@app.exception_handler(UnsupportedFileTypeError)` ever got a chance to return `415`. An unsupported file type came back as `422` instead of `415`, caught by a dedicated test. **Fixed** by removing the redundant local catch; exceptions now propagate to the two app-level handlers in `main.py`, the single place mapping domain exceptions to HTTP status.

**Ruff's B008 flags every `Depends(...)` default as a mutable-default bug.** That's FastAPI's standard DI pattern, not a real bug — the call is evaluated once per request by FastAPI itself. Rather than `# noqa` on every route parameter (which was about to be most of them), added `extend-immutable-calls = ["fastapi.Depends", ...]` to `pyproject.toml`'s ruff config.

**A CSV upload can contain multiple products, breaking `/evaluate`'s single-object contract.** `CsvExtractor` yields one row per product, so a multi-row CSV legitimately produces multiple `EvaluationResult`s — but the README's response shape is a single object. **Original decision (superseded, see Post-Phase 9 below):** `/evaluate` accepted CSV only when it resolved to exactly one row; 0 or 2+ rows returned `400` pointing the caller at the separate `/evaluate/batch`.

**`routes_products.py` (`GET /api/products`) wasn't in Phase 7's sub-task list, added anyway.** `ARCHITECTURE.md` Section 10 lists it, and Phase 6 built `EvaluationRepository.list_evaluations()` specifically to back it; leaving it unwired would make that method dead code. Documented as a deliberate scope pull-forward, not scope creep.

**Default sample-dataset paths point outside `backend/`.** `default_forbidden_list_path`/`sample_data_dir` resolve to the repo root via `parents[3]`, since that's where the real `images/`/`pdfs/`/`texts/`/`product_index.csv`/`forbidden_ingredients.csv` actually live. Degrades gracefully today (missing list → empty + warning). Flagged as a Phase 10 risk: a `backend/`-only Docker image needs the dataset copied in or the two path env vars set explicitly.

## Phase 8: Optional AI Tiers

**Tier 6 cannot be "registered into the MatchPipeline" as originally planned — it's a product-level async stage instead.** `Agent.run` is async; `MatchPipeline.match_ingredient`/`Matcher.match` are synchronous, called per `(ingredient, forbidden_entry)` pair with no product-level context, from inside a plain list comprehension in `decide()`. Worse, `app.state.match_pipeline` is a single instance shared across products evaluated concurrently under `evaluate_paths_concurrently`'s bounded semaphore — a matcher that tried to accumulate "all of this product's unresolved ingredients" as state between `match()` calls would interleave unrelated concurrent products. **Decision:** tier 5 (embedding) registers into `MatchPipeline` exactly as planned, since it's genuinely synchronous and per-pair. Tier 6 (LLM) is invoked once per product as an `await` step in `services/evaluation_service.py`, *after* `decide()` — never registered as a `Matcher`. `domain/decision/engine.py` gained two small pure helpers (`unresolved_ingredients`, `merge_llm_matches`) rather than making `decide()` itself async, so its existing synchronous tests stay untouched.

**Empirically confirmed (not just "likely"): tier 5 embeddings cannot catch the README's `Glucose`/`D-Glucopyranose` example either, and by a wider margin than fuzzy.** Scored with the real `all-MiniLM-L6-v2` model: `Glucose` vs `D-Glucopyranose` = 0.35 cosine similarity. The max similarity across every (ingredient, forbidden-entry) pair among the 6 samples that must stay Accepted is 0.75 (`Sodium Metabisulfite` vs `Sodium Lauryl Sulfate`, P-2025-0022) — or 0.85 if formula-shaped strings aren't excluded (`C6H8O7` vs `C6H6`, pure character overlap). Any threshold that would catch the README example (0.35) would false-reject a real Accepted sample first. **Decision:** exclude formula-shaped ingredients from tier 5 entirely (tier 2 already handles them exhaustively and precisely; embedding similarity between formula strings is pure character-overlap noise), and set the threshold conservatively at 0.90 — same precedent as tier 3's fuzzy threshold. Verified against the real model in `tests/unit/test_embedding_pipeline_regression.py` (skipped unless the model is already cached locally, so `pytest` still passes fully offline).

**`sentence-transformers` pulls in torch — kept out of the base `requirements.txt`.** Moved both optional-tier dependencies (`sentence-transformers`, `pydantic-ai`) into a separate `requirements-ai.txt`. The embedding encoder loader (`infra/embeddings/sentence_transformer_encoder.py`) imports `sentence_transformers` lazily inside a function, never at module scope, so `app.main` (and the whole test suite) imports cleanly with neither package installed — verified by inspecting `sys.modules` after importing `app.main` with both flags off.

**The LLM response cache has no `ForbiddenListVersion` row to key against.** That table only exists when persistence is enabled, but the cache must work regardless. **Decision:** added `ForbiddenListRepository.version_hash()` — a SHA-256 of the sorted, case-folded entry set — as the version component of the tier-6 cache key, so a `POST /forbidden-ingredients` upload always invalidates stale LLM verdicts by construction (a new list produces a new hash), with no dependency on persistence being on.

**Manual Gemini smoke test (real API key, not committed): tier 6 works exactly as designed.** Borrowed a `GEMINI_API_KEY` from an unrelated local project for a one-off, uncommitted local call (never written to any file in this repo). `D-Glucopyranose` vs forbidden `Glucose` → matched, confidence 1.0, rationale correctly identifies it as the IUPAC name for glucose. `Sodium Laureth Sulfate` vs forbidden `Sodium Lauryl Sulfate` (the real sample's near-miss) → correctly returned no match. Confirms the tier is both the only path that catches the README's naming-convention example *and* precise enough not to reintroduce the SLES/SLS false positive tiers 3-5 were built to avoid.

**Real bug, caught only by running the full 30-sample batch against a live Gemini call, not by any unit test.** With tiers 5 and 6 both enabled against real backends, P-2025-0022 flipped from its correct `Accepted` to a false `Rejected`: the LLM matched `C6H8O7` (citric acid) to forbidden `C8H10N4O2` (caffeine) — two chemically unrelated formulas — at confidence 1.0, with a fabricated-sounding rationale. A mocked-client unit test can never catch this class of bug, since the mock only ever returns what the test tells it to; only a real model call against real data surfaced it. **Fix:** `LlmMatcher.match_unresolved` now filters out any `is_formula(ingredient)` ingredient before it ever reaches the LLM, mirroring tier 5's formula exclusion — tier 2 already resolves formula equality exhaustively and precisely, and an LLM has no reliable way to verify formula equivalence through text reasoning alone, so it must never be asked to. Re-ran the full 30-sample batch against the same live Gemini key after the fix: 0 mismatches. Regression-guarded in `tests/unit/test_llm_matcher.py::test_formula_shaped_ingredients_are_never_sent_to_the_llm` (using this exact real pair as the test data, not a synthetic stand-in).

**Honest caveat on what the live batch run actually proves:** across all 30 real samples, tier 6 produced *zero* matches after the fix — every forbidden ingredient actually present in the dataset is already caught by tiers 1-4. So "0 mismatches with tier 6 live" confirms tier 6 doesn't break anything on real data; it does not by itself demonstrate tier 6 finding something tiers 1-5 missed. That demonstration came from a separate, synthetic test: uploading a forbidden list containing just `Glucose` and evaluating a product containing `D-Glucopyranose`, which tier 6 correctly caught (see the manual smoke test entry above). Tier 6 is empirically load-bearing for the README's stated naming-convention requirement, not for anything in the provided sample dataset.

## Post-Phase 9: Consolidate `/evaluate` to accept multiple files

**Request:** add a way to upload more than one file at once. The backend already had a separate `/evaluate/batch` endpoint doing exactly this (built in Phase 7) — the actual gap was the frontend never exposed it. First pass added a second "upload multiple files" section to the Evaluate page calling `/evaluate/batch`, but the user asked for something simpler: one upload control that optionally accepts more than one file, and one backend endpoint rather than two.

**Decision:** merged `/evaluate/batch` into `/evaluate`. The route now takes `files: list[UploadFile]` (repeated `files` multipart field, replacing the old singular `file` field — a deliberate breaking change to the field name, accepted since the user explicitly asked for this consolidation) and its response shape depends on what the request resolves to:
- Exactly one file that itself yields exactly one product row → the single README-shaped `EvaluationResult` (`response_model=EvaluationResult | BatchEvaluationResponse`, which FastAPI/Pydantic renders as an `anyOf` in the OpenAPI schema — confirmed by inspecting `/openapi.json` directly).
- Anything else (2+ uploaded files, or a single CSV file whose rows expand to more than one product) → `BatchEvaluationResponse`.

This also **changed** the multi-row-CSV behavior: previously a lone multi-row CSV returned `400` pointing the caller at `/evaluate/batch` (a real workaround, since that endpoint didn't have the single-file "exactly one row" restriction). Now the same CSV, uploaded alone, just returns the batch shape directly rather than erroring — a behavior improvement that fell out of the consolidation for free.

**Preserved on purpose:** the single-file error path does NOT go through the error-isolating multi-file code path. A single bad-type upload still raises straight to the app-level exception handlers (`415`/`422`), exactly as before — verified live (`curl` returned `415` for a single bad-type file, `422` for zero files, both before and after touching the frontend). Only when 2+ files are uploaded does a bad file get isolated into an `"error"` batch item instead of failing the whole request, matching the old `/evaluate/batch` semantics.

**Verification:** full backend suite (165 tests) and `ruff check` pass; new/updated tests cover single-file (unchanged 415/422/README-shape behavior), multi-row single CSV (now batch shape, not `400`), and 2+ files (both good, and good+bad isolation). Live-server `curl` checks against all five cases (single, two-good, multi-row-CSV, zero-files, bad-type) matched expectations exactly. Frontend: `npm run build`/`npm run lint` pass; real-browser (kimi-webbridge) click-through confirmed uploading 2 files renders both rows in Results with a "2" badge, and a subsequent single-file upload through the same control still adds one row and preserves the single-object contract end-to-end.

## Post-Phase 9: Implement the LLM extraction fallback, and add token usage/cost tracking

**Found while reviewing the codebase for stale TODOs.** `domain/parsing/llm_fallback.py` had carried a `# TODO(Phase 8): implement a concrete LlmExtractionFallback...` since Phase 3, and its module docstring claimed the concrete implementation "is wired in Phase 8" — false. Phase 8 only built tiers 5/6 for *matching*; the `ExtractedProduct.needs_llm_fallback` flag (set by both `product_parser.py` and `csv_product_parser.py`, and asserted on by three test files) was computed but never consumed by anything downstream — a file with no detectable ingredients section just silently evaluated as if it had zero ingredients (usually `Accepted`), with no LLM ever attempted.

**Fix:** implemented `LlmExtractionFallback` (raw port) / `LlmFallbackExtractor` (timeout + fail-open wrapper, mirroring `LlmMatcher`'s design) in `domain/parsing/llm_fallback.py`, and a concrete `PydanticAiExtractionFallback` adapter in `infra/llm/pydantic_ai_extraction_fallback.py`. Wired into `evaluate_products_from_file`: any product (from a text/pdf/image blob, or a CSV row rendered as `key: value` lines) flagged `needs_llm_fallback=True` is retried through the LLM before matching runs. Gated behind the same `ENABLE_LLM_MATCHING`/`GOOGLE_API_KEY` toggle as tier 6, rather than a second flag — both are "is Gemini configured," and the app's zero-config default already means neither runs without a real key.

**Requested alongside this: show which matching method was used, and — specifically for LLM — the token usage and cost.** The per-match `method` badge already existed since Phase 9 (`MatchList.tsx`); the actual gap was cost/token visibility. Investigated via Context7 against the installed `pydantic-ai==2.18.0`: `AgentRunResult.usage` is a plain attribute (not the `.usage()` method some older docs/versions show), giving `RunUsage(input_tokens, output_tokens, requests)` with a computed `total_tokens`. `AgentRunResult` itself has **no** `.cost()` method in this version (only `Embedder`'s `EmbeddingResult` does) — confirmed by inspecting the installed class directly rather than trusting a docs example. Cost is computed via `genai_prices.calc_price(usage, model_ref, provider_id="google")` — `genai-prices` is already a transitive `pydantic-ai` dependency with a maintained per-model pricing database (verified live: correctly priced `gemini-3.1-flash-lite` at $0.25/1M input, $1.50/1M output tokens), chosen over a hand-maintained price table so it tracks provider pricing changes automatically. If a model isn't in that database, cost fields are `None` rather than a guessed number.

**Deliberately kept out of `output_type`.** `LlmMatchResponse` (tier 6) and the extraction fallback's internal `_ExtractedFields` schema are exactly what's handed to the Pydantic AI `Agent` as `output_type` — the schema the model itself fills in. Usage is metadata about the API call, not something to ask the model to report on itself (it would have Gemini inventing its own token counts). The concrete adapters build a separate envelope (`LlmClientResult` for tier 6, `LlmExtractionOutcome` for the fallback) combining `result.output` with `result.usage` *after* the call returns.

**Usage flows out via return values only, never shared instance state.** `app.state.llm_matcher`/`app.state.llm_extraction_fallback` are singletons shared across concurrently-evaluated products under `evaluate_paths_concurrently`'s semaphore (up to 8 at once); stashing "last call's usage" as mutable state on the client would let concurrent products clobber each other's numbers. `LlmMatcher.match_unresolved` and `LlmFallbackExtractor.extract` both return their usage directly, and `domain/decision/engine.py` gained `_combine_usage` (sums tokens/cost, treating a missing cost side as 0 rather than nulling the total) so a product that goes through both the extraction fallback and tier 6 gets one combined `EvaluationResult.llm_usage`.

**Not persisted.** `SqliteEvaluationRepository` stores `EvaluationResult` as discrete columns (`product_name`, `status`, `reason_json`, `matches_json`), not a full JSON blob — `llm_usage` isn't in that list, so persisted/historical evaluations (`GET /api/products`) won't show cost even when the live response did. Adding a column was out of scope for this pass; noted here rather than silently dropped.

**Real bug #2 caught by live testing, same class as the citric-acid/caffeine one from Phase 8, mirror-image gap.** Live-tested the extraction fallback with a synthetic file (`Ingredients: Aqua, Glycerin, Coumarin, Dimethicone`, no "Chemical Formulas" header so the regex parser skips it) against the real 13-entry forbidden list. The LLM correctly recovered all four ingredients and tier 1 caught `Coumarin` exactly -- but tier 6, given the remaining unresolved `Aqua`/`Glycerin`/`Dimethicone` against the full forbidden list, matched `Aqua` (INCI name for water) to forbidden `H2O2` (hydrogen peroxide) at confidence 1.0. Water and hydrogen peroxide are not the same substance. Root cause: `LlmMatcher.match_unresolved` filtered `is_formula` on the *ingredient* side only (per the original Phase 8 fix), never on the *forbidden entry* side -- but tier 5's `EmbeddingMatcher.match` had always excluded both sides (`is_formula(ingredient) or is_formula(forbidden_entry)`), so tier 6 was inconsistent with its own sibling tier and exposed exactly the gap that inconsistency left open. **Fix:** filter `forbidden_list` to non-formula entries before it's ever offered to the LLM, mirroring tier 5 exactly; short-circuit with no API call if that leaves nothing to check against. Regression-guarded in `test_llm_matcher.py::test_formula_shaped_forbidden_entries_are_never_sent_to_the_llm`. Re-ran the same live request after the fix: `Aqua` correctly resolved to no match, only `Coumarin` (exact) in the result.

**Honest caveat: this fix has a real cost, not just a win.** Excluding formula-shaped forbidden entries means a product listing an ingredient by common/trade name against a forbidden entry given only as a formula is now unmatchable by *any* tier -- e.g. an ingredient labeled `Benzene` against forbidden `C6H6`: tier 2 won't fire (`Benzene` itself isn't formula-shaped, so the formula matcher has nothing to parse), tier 5 already excluded this pair, and tier 6 now excludes it too. This trade is the same one already made for tier 5 and for the SLES/SLS precision-over-recall call in Phase 5/8: precision over recall on formula/common-name pairs, since an LLM asked to verify chemical identity through text reasoning alone has already produced two confirmed hallucinations (citric-acid/caffeine, water/hydrogen-peroxide) and no confirmed correct catch of this specific pairing shape. The 30-sample live batch shows zero real-data impact (0 mismatches), but that only proves this exact dataset doesn't exercise the gap -- not that the gap is free in general.

**Live verification performed (real Gemini API, real key, nothing mocked):**
- Naming-variant catch end-to-end: replaced the forbidden list with just `Glucose` via `POST /forbidden-ingredients`, evaluated a product containing `D-Glucopyranose` -- correctly `Rejected`, `method: llm`, confidence 1.0, real `llm_usage` (309 input / 66 output / 375 total tokens, ~$0.000176). Re-ran the identical request: `llm_usage: null` (served from cache, confirming no double-spend).
- Extraction fallback end-to-end (see bug #2 above for the full scenario) -- confirms a file with no detectable ingredients section is genuinely retried through Gemini and recovers real ingredients, not just theoretically wired.
- Full 30-sample live batch (`/evaluate/batch-samples`, both `ENABLE_EMBEDDING_MATCHING` and `ENABLE_LLM_MATCHING` true, real key) after the fix: 0 mismatches against the hand-derived ledger, 0 errors, 21/30 results carrying real `llm_usage` (tier 6 queried but found nothing new on the real dataset, consistent with the Phase 8 finding above that tiers 1-4 already catch everything present) -- confirms the `LlmMatchOutcome`/return-type refactor and the new forbidden-entry filter didn't regress anything.
- Real-browser (kimi-webbridge) click-through against the actual frontend: uploaded the Glucose-variant CSV, confirmed the Results row expands to show the `llm` method badge on the match plus an `LlmUsageSummary` line ("LLM · 369 tokens · $0.000167 estimated cost"). Separately uploaded a file that resolves to `Accepted` with zero matches but real tier-6 usage, confirmed the row still shows a `▼ show details` affordance (reason is `—`, no matches) and expands to the usage line alone -- validates the row is expandable on usage presence, not just match presence.
- `ENABLE_LLM_MATCHING`/`ENABLE_EMBEDDING_MATCHING` were temporarily flipped to `true` in the local (untracked, gitignored) `.env` for this testing and reverted to `false` afterward, matching how the repo was found; the forbidden list was restored to the real 13-entry `forbidden_ingredients.csv` (in-memory only, `POST /forbidden-ingredients` never touches the file on disk) by restarting the test server.

**Verification:** full backend suite (178 tests, 13 new) and `ruff check` pass. Every fake client shape that changed (`FakeLlmClient`, `HangingLlmClient` in `test_llm_matcher.py`; `_FakeLlmClient` in `test_routes_evaluate_llm.py`; the extraction fallback fakes) was updated and re-run in the same pass, not left to bit-rot. New tests cover: usage attached only when a real call is made (not on a pure cache hit), fail-open leaving `llm_usage=None`, the extraction-fallback-then-tier-6 combined-usage path, and both formula-exclusion directions (ingredient and forbidden-entry). Frontend: added `LlmUsageSummary.tsx`, wired into `ResultsPage.tsx`'s expandable row (now expandable whenever there's a match *or* usage to show, not just matches); `npm run build`/`npm run lint` pass.
